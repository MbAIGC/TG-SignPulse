## 1. 结论

两个仓库同源于 `akasls/TG-SignPulse`，但**已经实质分叉，不存在"谁版本号大谁更全"**：

- 参照仓库在**签到回复可靠性、断线消息恢复、账号巡检、容器加固、页面内更新**上比本仓库完善；
- 本仓库在**自动化规则引擎、签到记录存储、运行状态机、账号锁、登录审计与限流、测试与 CI**上明显领先。

因此正确的做法是**按能力项选择性借鉴**，而不是整体对齐或回退。本文件按"该不该改、收益多大"排序，逐项给出证据与建议。

## 3. P0：会静默骗过用户或丢消息

### 3.1 多会话签到部分失败仍写入"当日已签到"

- **问题**：`sign_once()` 只统计 `success_count`，被 `except errors.RPCError` 吞掉的失败会话不阻断流程；只要有一个会话成功，就会执行 `persist_sign_record()` 把当天标记为已完成，`need_sign()` 之后不再补签。结果：**漏签但面板显示成功**。
- **证据**：`tg_signer/core.py:2182-2206`（`if success_count == 0 and len(config.chats) > 0: raise`，随后无条件 `persist_sign_record`）。
- **参照做法**：收集全部失败，任一失败即抛，且仅在无失败时写记录；异常按 `OSError`（网络，交后端重试）与其他分流。见参照仓库 `tg_signer/core.py:1413-1449`。
- **建议**：改为"任一会话失败即整轮判失败且不写记录"，并保留逐会话失败详情到日志。这是与"签到工具"核心价值直接冲突的问题，优先级最高。

### 3.2 执行日志跨账号串台，并连带取错机器人回复

- **问题**：
  1. `TaskLogHandler` 只接收一个列表，不接收账号/任务/run_id，也不 `addFilter`；`emit()` 无条件 append。所有账号共用 `logging.getLogger("tg-signer")`，同一 handler 集合会收到全部记录 → **A 账号的日志被写进 B 账号的缓冲区**。
  2. 更实质的后果：判定"机器人最后回复"时只匹配 `"收到来自「"`，**不校验账号/任务前缀**，并发运行时会取到别的账号的回复并据此判定成败。
- **证据**：`backend/services/sign_tasks.py:58-75`（handler 定义）、`:3824-3831`（挂载）、`:3994-4002`（回复归属）。
- **参照做法**：`contextvars.ContextVar` 记录 `(account, task, run_id)`；`_AccountTaskLogFilter` 三级判定（LogRecord 显式身份 → ContextVar → 日志前缀正则 `账户「(?P<account>.*?)」- 任务「(?P<task>.*?)」:`）；`BackendUserSigner.log()` 把身份注入每条记录；回复归属处构造 `expected_task_prefix` 再匹配。见参照仓库 `backend/services/sign_tasks.py:102-133`、`:149-154`、`:2078-2085`。
- **建议**：引入等价机制。本仓库已有 `RunContext`（含 `run_id`）但只作标识用，把它接入日志过滤即可，不需要新增状态存储。

### 3.3 实时日志缓冲打满后停止推送

- **问题**：`TaskLogHandler.emit()` 在超过 1000 行时 `pop(0)`（`sign_tasks.py:72-73`），而 WS 推送判断是 `if len(active_logs) > last_idx`（`backend/api/routes/sign_tasks_v2.py:750, 767-776`）。缓冲区达到稳态长度后长度恒等，**新日志不再推送**，面板表现为日志中途卡住。DB task 的日志桥接（`backend/services/tasks.py:239-240, 253-267`）是同一模式、同一缺陷。
- **参照做法**：`LogBuffer` 携带累计序号 `total` 与 `run_id`；`slice_logs_since()` 用 `max(cursor, oldest)` 计算起点，滚出部分自动跳过、永不因 maxlen 停推；WS 接受 `run_id/cursor/monitor_cursor` 支持断点续传。见参照仓库 `backend/services/sign_tasks.py:53-72`、`:1812-1827`。
- **建议**：改为累计序号推送并让 WS 接受游标；前端同步支持重连续传（见 §6.2）。

### 3.4 更新同步失败被伪造成"已同步"并丢弃消息

- **问题**：`_patched_invoke` 对 `GetDifference`/`GetChannelDifference` 重试耗尽后，**返回 `DifferenceEmpty` / `ChannelDifferenceEmpty`** 并打印 `Drop updates for ...`。SDK 会认为已同步到 `query.pts`，该区间消息永久不再回补。这是"签到收不到回复"的根因级差异之一。
- **证据**：`tg_signer/core.py:316-356`（重试 → warning → 伪造空响应）。
- **参照做法**：`tg_signer/update_guard.py`（1003 行）替换 `BaseClient.handle_updates`：先投递消息再推进持久化游标；短消息 `UpdateShortMessage/UpdateShortChatMessage` 用 `GetDifference` 补差并按失败指数退避；频道差异 single-flight + 退避 + 全局 4 槽并发租约；`DifferenceTooLong` 按 Telegram 要求重定基线。见参照仓库 `tg_signer/update_guard.py:370-440`、`:618-863`、`:273-316`。
- **建议**：不要原样移植（内核版本不同）。最小可行方案是先**去掉"伪造空响应"**，改为失败后保留游标并重试，避免静默丢消息；完整的 gap 恢复能力作为专项立项，配套可复现的回归用例。

## 4. P1：可靠性缺口

### 4.1 预检 TIMEOUT / CONNECTION_ERROR 不阻断签到

- 本仓库：`_check_account_before_task()` 异常一律 `return None`（`backend/services/sign_tasks.py:1897-1904, 1926`），调用方视为"检查通过"继续签到，把短时网络抖动放大为连续失败。
- 参照仓库：返回 `ok/invalid/transient` 三元状态，`transient` 时**跳过本次签到**并记录"将按计划重试"（`backend/services/sign_tasks.py:986-1039`、`:1895-1912`）。
- 另：本仓库 `check_account_status()` 的 `ConnectionError` 分支一律返回 `CONNECTION_ERROR`（`backend/services/telegram.py:542-551`），丢失 session 失效语义；`"SESSION"+"INVALID"` 宽匹配（`:570`）易误判，参照方只匹配精确错误码。

### 4.2 调度层没有失败自动重试

- 本仓库 `backend/scheduler/__init__.py` 中 `retry` 零命中；任务失败只写日志。
- 参照仓库 `TASK_RETRY_DELAY_SECONDS = 600`，失败后注册一次性 `DateTrigger` 重试 job，账号失效不重试、重试本身失败不再二次重试（`backend/scheduler/__init__.py:85-149`）。

### 4.3 range 模式窗口内不补执行

- 本仓库的随机等待是进程内 `await asyncio.sleep(delay_seconds)`（`backend/scheduler/__init__.py:159`），进程重启即丢失，当天不会补跑；新建/编辑任务落在窗口内也不补。
- 参照仓库用 APScheduler `DateTrigger` 注册一次性 job，并有 `schedule_range_catchup()`（依赖 `last_run` 判断今日是否跑过、`_has_pending_job` 防重复）。
- 本仓库现有的 `misfire_grace_time=3600` 只对 CRON 触发生效。

### 4.4 历史日志截断方向相反

- 本仓库 `_normalize_flow_logs()` 取 `flow_logs[: max_flow_lines]`，**保留头部、丢掉尾部**，而失败原因与最后回复总在末尾；超长行截断也不加省略号（`backend/services/sign_tasks.py:893-908`）。
- 参照仓库保留尾部 `flow_logs[-max_lines:]`，超长行以 `...` 结尾（`backend/services/sign_tasks.py:414-433`）。
- 修复成本极低、收益直接（排障时看得到失败原因）。

### 4.5 `task_runs` 表只增不删

- `backend/services/run_state_store.py` 只有 `save/latest_states/get`，**没有任何 DELETE**；`_cleanup_old_logs()` 只清 JSON 与 `run_history` 表（`backend/services/sign_tasks.py:447-467`），每日维护也不碰 `task_runs`。每次运行留一行，且启动时 `latest_states()` 要做全表 `GROUP BY`，随运行次数线性变慢。
- 建议：加按时间/条数的清理，与 `run_history` 一致。

### 4.6 关键词监听无看门狗

- 本仓库：`await client.__aenter__()` 无超时（`backend/services/keyword_monitor.py:1754`），失败只记一条 warning（`:1753-1775`），无重试调度；"连接标志正常但实际无响应"只能等配置变更或进程重启。`_handlers_are_active_for()` 也只检查 `is_connected`，不检查 `is_initialized`（`:651-659`）。
- 参照仓库：30s 周期真 RPC 探测（`get_me` + `MONITOR_HEALTH_TIMEOUT=8`）、连续 2 次失败才重建、`FloodWait` 不计入失败、探测前跳过正持账号锁的账号、启动失败 30→300s 指数退避、`stop()` 特判不取消看门狗自身（`backend/services/keyword_monitor.py:1635-1715`）。配套 6 个回归测试文件。
- 本仓库 `tests/` 目前对关键词监听、看门狗、update guard **零覆盖**。

### 4.7 账号改名/删除路径不取账号锁

- `backend/api/routes/accounts.py` 中 `get_account_lock` 零命中，而 `rename_account_references()`（`backend/services/sign_tasks.py:2766-2873`）会移动目录、重写 config/history，并搬迁 `_active_logs/_active_tasks/_cleanup_tasks` 的 key。与在跑任务并发时存在数据与状态不一致风险。
- 参照仓库在这些路径取账号锁（`backend/api/routes/accounts.py:620, 711`）。

### 4.8 客户端生命周期语义粗糙

- 本仓库：`__aenter__` 手搓 `connect() → get_me() → GetState() → initialize()`（`tg_signer/core.py:553-636`），而非让 `start()` 负责完整序列；`__aexit__` 减引用归零后直接 pop 实例与锁（`:661-681`）；`close_client_by_name` 在锁外 `stop()`、无"正在关闭"守卫（`:794-852`）；清理无 `asyncio.shield`，被取消时可能停在中间态。
- 参照仓库：引用计数与锁归属**实例**（避免旧引用误操作替换后的新实例）、`_CLIENT_CLOSING` 防重入、`_finalize_client_resources` 分级兜底（stop → 取消 watchdog/dispatcher → disconnect → session/connection → storage）、`_complete_client_cleanup` 用 `asyncio.shield` 保护（`tg_signer/core.py:180-322, 412-420, 537-563`）。
- 本仓库更强的地方：`::memory` 缓存键隔离内存/文件会话、`close_all_clients()`、共享实例断线时 `__aenter__` 会重连、`_ensure_app_ready()` + `_call_with_retry()` 提供显式重连与退避。**重构时不要丢掉这些。**

### 4.9 监听 handler 与签到同在 group 0（推断）

- 本仓库监听 `client.add_handler(MessageHandler(...))` 不带 group（`backend/services/keyword_monitor.py:1747-1752`），签到 handler 也是默认 group 0（`tg_signer/core.py:2223, 2226`）。
- 参照仓库监听用 `group=MONITOR_HANDLER_GROUP = 10`（`backend/services/keyword_monitor.py:37, 1581`），并有测试断言"监听与签到都能收到同一条消息且互不干扰"。
- **标注**：本仓库是否存在实际抢占，未实测（Pyrogram 同组内按注册顺序投递），需构造复现后再改。

### 4.10 关键词命中推送无异常保护

## 5. P2：安全与部署

### 5.1 容器以 root 运行，compose 无加固

- 本仓库 `Dockerfile` 无 `USER` 指令，`docker/` 是空目录，无 entrypoint；`docker-compose.yml` 缺 `cap_drop: ALL`、`no-new-privileges`、`read_only`、`tmpfs`、`init`、`stop_grace_period`、日志大小上限。
- 参照仓库：非 root 用户（UID/GID 10001）+ `docker/entrypoint.sh`（按 `/data` 属主自适应运行身份、修复历史文件属主与写位、docker.sock 属组注入）+ compose 全套加固。
- **这也是"一键更新"的前置条件**：在当前 root 容器上开放 docker.sock，等于把宿主机 root 交给任何拿到面板登录态的人。

### 5.2 静态托管：未知 `/api/*` 返回 HTML 200，路径判定用前缀匹配

- 本仓库 `backend/main.py:230-254` 没有 `api/` 提前 404 分支，有构建产物时会返回 `index.html` + 200；SPA 兜底用 `str(...).startswith(str(resolved_web))`（`:243, 247`），同前缀兄弟目录可穿越。本仓库 `doc/upstream-sync-decision-table.md` 已把该前缀问题登记为未修项。
- 参照仓库用 `candidate.is_relative_to(WEB_DIR)` 并显式 `api/` → 404（`backend/main.py:162-170, 182-183`）。
- 另外本仓库 `/assets` 无 `Cache-Control`（参照仓库给哈希资源加 `immutable`，代码变更需改挂载名）。

### 5.3 `POST /api/user/totp/reset` 只要 JWT + 密码即可关闭 2FA

- 本仓库 `backend/api/routes/user.py:326-340` 仅校验密码，不要求 TOTP 验证码，与同文件 `/totp/disable`（`:297-323`，要求验证码）不一致。这是一条"拿到会话令牌 + 知道密码即可永久关闭两步验证"的降级路径。
- 参照仓库已删除该接口，改为服务器终端 CLI（`backend/cli/reset_totp.py`）。本仓库的 CLI 兜底已存在（`backend/cli/admin.py:7, 109-123`）。
- 建议：删除该接口，或改为强制要求 `totp_code`；前端残留封装 `frontend/src/lib/api.ts:104-108` 同步清理。
- 注意：`POST /api/auth/reset-totp`（`backend/api/routes/auth.py:193-260`）是**有意保留**的裁决项——已有限流 + 服务端应急密钥 + 等时比较，属充分鉴权，不必照搬删除；应补的是给 `APP_EMERGENCY_RESET_KEY` 加最小长度校验并写进 `.env.example`。

### 5.4 `APP_SECRET_KEY` 并发首启无锁、写入非原子

- 本仓库 `backend/core/config.py:116-130`：`read_text`/`write_text` 无进程间锁；两个 worker 并发首启可能各自生成密钥、内存中各持一份，导致 A 签发的 JWT 在 B 校验失败；已有密钥文件不校验长度、不收紧权限。
- 参照仓库用 `flock`（独立锁 inode）+ 锁内重读 + `mkstemp/fsync/os.replace` 原子替换，且每次读取都 `chmod 0600`（`backend/core/config.py:25-66`）。
- **保留**本仓库更严的部分：弱值/过短值直接拒绝启动、生产环境无法持久化密钥时拒绝启动。

### 5.5 没有每日账号健康巡检

- 本仓库 `backend/scheduler/__init__.py` 只注册 03:00 维护任务，**无巡检 job**；`check_account_status()` 的消费方只有任务前预检与批量状态接口（后者只返回结果，不落 `needs_relogin`、不发通知）。
- 参照仓库有 `0 9 * * *` 的 `_job_health_check_accounts()`（`backend/scheduler/__init__.py:215-260, 488-494`）与手动端点 `POST /api/accounts/health-check`（`backend/api/routes/accounts.py:456-469`）。
- **本仓库已具备全部底层机制**：`_mark_account_invalid()` 与 `invalid_notified_at` 通知去重（`backend/services/sign_tasks.py:1795-1863`）。只缺"一个 cron 注册 + 一个路由"，是性价比最高的一项。建议同时用账号锁避免与在跑任务争用会话。

### 5.6 CI 发布纪律

- 本仓库：`latest` 在 main 推送也会刷新；无版本/tag 一致性校验；无 PR 阶段镜像冒烟；无 `concurrency`；仅 `linux/amd64`。
- 参照仓库：仅正式 tag 推 `latest`、强制 `tag == v{version}`、PR 冒烟构建、`concurrency` cancel-in-progress、docs-only 跳过、`linux/amd64,linux/arm64`。
- **不要照搬**：参照仓库的 CI 完全不跑 ruff/pytest/前端构建；本仓库的 `lint-test-build.yml` 是领先项，应保留并只补发布纪律与多架构。

## 7. 本仓库领先、明确**不要**照搬的部分

1. **账号锁**：跨进程 `flock` + 非阻塞轮询 + 超时（`backend/utils/account_locks.py`）；参照仓库只有 13 行纯进程内 `asyncio.Lock`。
2. **运行状态机**：SQLite `task_runs` + `worker_id=pid@hostname` + `os.kill(pid, 0)` 存活判定 + 重启自动改判 `cancelled`；`/run/start`（后台立即返回）、`/run/status`、`/run/cancel`（run_id 校验）。参照仓库只有阻塞式 `/run`。
3. **任务级原子占位**：`RunCoordinator.try_reserve` + `_run_start_locks`。参照仓库依赖"check 与 set 之间无 await"的隐式原子性。
4. **安全与审计**：登录限流 + `LoginLog` 审计 + 代理头信任开关（`APP_TRUST_PROXY_HEADERS`）+ access log IP 脱敏 + 生产禁用 `/docs`、`/redoc`、`/openapi.json` + 用户名枚举等时处理。参照仓库这些基本没有，且**无条件信任 `X-Forwarded-For`**。
5. **CI 质量门禁**：ruff + pytest + 前端构建；参照仓库完全没有。
6. **库层能力**：`daily_times` 每日多次（1–5 次，参照方无）、`(chat_id, message_thread_id)` 的 RouteKey 路由、点击后跟进判定、`SIGN_TASK_EXECUTION_TIMEOUT`、`_call_telegram_api` 统一限流与 FloodWait、`::memory` 会话分离、`close_all_clients()`。
7. **监听能力**：话题 ID 五路候选、随机延迟区间（`"3-8"`）、Inline + ReplyKeyboard 按钮收集、AI `system_prompt`、全部后续动作带重试与重连、话题不匹配/关键词未命中的节流诊断日志。
8. **`/data` 不可写降级 `/tmp`**：两边实现逐字相同（`backend/utils/storage.py:84-103`），不是差异项。
9. **`/healthz`、`/readyz`**：语义等价，本仓库额外有 `/health` 别名与探针日志过滤测试。
