# TG-SignPulse main 分支 Bug 修复规划

## 基线

- 分支：`main`
- 基线提交：`0b0eebe`
- 当前 Python 测试：214 项通过

## 目标与原则

1. 先消除会导致重复执行、状态永久 running、历史丢失的发布阻塞问题。
2. 所有修复都配套最小可复现回归测试，优先覆盖并发、异常和重启场景。
3. 保留现有 JSON 兼容能力，SQLite 继续作为运行历史主存储。
4. 不引入 Telegram/OpenAI 真实调用，外部依赖场景用 mock 验证控制流。

## 执行顺序与验收标准

### P0-1：统一任务并发占位和账号锁边界

- 在 `backend/services/tasks.py` 的账号锁内重新检查同一 task 的运行状态。
- 修复 `SignTaskService.start_task_run()` 的 task-key 级原子占位：检查、生成 run_id、登记 running、注册后台 runner 必须由同一把 asyncio 锁保护。
- 统一 runner 创建失败、取消和异常时的状态及 active 标志清理。
- 验收：并发 `gather()` 只产生一个 runner/run_id；同一 task 不重复执行；异常后可以再次启动。

### P0-2：统一 run/status/history 标识

- 让 `/run` 直调路径也创建并传递唯一 `run_id`，终态写入状态文件并与历史条目一致。
- 避免 `_save_run_info()` 在已有执行上下文中生成第二个 run_id。
- 验收：`/run`、`/run/start`、DB task 的状态和历史可通过同一 run_id 关联。

### P0-3：修复历史 SQLite 事务与账号隔离

- `RunHistoryStore.save_entry()` 将插入和截断放进同一事务。
- 明确并实现每个 `(task_name, account_name)` 独立保留上限，避免同名任务账号互相挤占。
- 增加唯一/稳定删除能力的基础，保留现有 API 兼容行为。
- 验收：两个账号并发写入互不截断；单次写入失败不会留下半截截断结果。

### P0-4：真正执行 flow 日志限制

- 应用 `SIGN_TASK_HISTORY_MAX_FLOW_LINES` 和 `SIGN_TASK_HISTORY_MAX_LINE_CHARS`。
- 保留原始行数并正确设置 `flow_truncated`，同时兼容异常输入。
- 验收：超行数、超字符数均按配置截断，数据库/JSON/API 使用截断结果。

### P1-1：幂等导入旧 JSON 历史

- SQLite 首次读取/初始化时导入旧 JSON，按 run_id 去重；无 run_id 的旧记录使用稳定摘要去重。
- 导入失败保留 JSON fallback，并记录 warning/debug。
- 验收：升级后旧历史不会因出现新 SQLite 记录而消失，重复初始化不会重复导入。

### P1-2：历史读取与写入原子性统一

- `_get_last_run_info()` 改为优先使用 `RunHistoryStore`。
- history/config JSON 写入统一使用项目原子写入工具。
- 重启把 running 标记为 cancelled 后立即持久化。
- 验收：SQLite 有记录时各读取入口一致；模拟写入失败不会产生损坏 JSON；重启状态文件为 cancelled。

### P1-3：补齐回归测试和质量门禁

- 增加并发启动、锁内二次检查、flow 截断、迁移幂等、历史账号隔离、异常清理测试。
- 执行 `ruff check`、`ruff format --check`、完整 pytest；前端构建按依赖可用性执行并记录结果。

## 实测运行卡住修复

- 修复 `/run/start` 后台 runner 被自身 `_active_tasks` 标记拦截的问题；该问题会使实际执行器未启动而界面持续显示“运行中/等待任务输出”；
- 后台 runner 显式授权复用本次已预留任务键，其他并发请求仍会被正常拦截；
- 任务日志弹窗保存启动响应的 `run_id`，轮询状态时精确查询本次运行，避免观察到同账号任务的其他运行；
- 新增后台预留运行确实进入执行器并落盘成功终态的回归测试。
